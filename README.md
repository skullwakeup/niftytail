# NIFTYTAIL

**Extreme Downside Risk Estimation in the Nifty 50 Using Extreme Value Theory.**

NIFTYTAIL measures the one-day extreme downside risk of the Nifty 50 index: Value-at-Risk (VaR) and Expected Shortfall (ES) at 95% and 99%, with 99.5% and 99.9% shown as descriptive levels. It compares six models on 5,716 out-of-sample trading days (rolling 1,000-day window, re-estimated every day): two unconditional benchmarks (Gaussian, historical simulation), a peaks-over-threshold Generalized Pareto model (POT-GPD), and three models on the residuals of one GARCH filter (GARCH-N, filtered historical simulation FHS, and GARCH-EVT). The threshold was selected and committed on the training data before any out-of-sample forecast was computed. The frozen plan excluded GARCH; the three GARCH-based models were added by a dated amendment (D38, D39), also before any out-of-sample forecast was computed ([docs/report.md](docs/report.md), section 7). Every published number is regenerated byte-for-byte from the code in the development repository (see [docs/reproducibility.md](docs/reproducibility.md)). This is research code from an internship project. Market data is never included in this repository.

## Headline result (holds in all three passes)

The claim policy (D49 T6) allows headline claims only for statements that hold in all three test passes (PR W1000, PR W2000, TRI W1000). Quoted verbatim from [docs/results_review.md](docs/results_review.md):

> **T1.** Holding in all three passes:
> - F1 (IND rejected for gaussian, hs and pot_gpd at both levels; not rejected for garch_n, fhs and garch_evt; garch_evt beats pot_gpd in DM family (ii) at both levels);
> - F4 (pot_gpd vs hs never rejected);
> - the F7 gaussian pattern;
> - garch_n rejects Kupiec and the ES test at 0.99.

Borderline in parts (p in [0.01, 0.10]): GARCH-EVT vs POT-GPD at 0.99, Holm p 0.0109754 on PR W1000 and 0.0105477 on TRI W1000 (`dm.conditional[a=garch_evt, b=pot_gpd].p_holm`); IND for GARCH-EVT at 0.95 on TRI W1000, p 0.0887 (`coverage.0.95.garch_evt.christoffersen.p_ind`); HS vs POT-GPD at 0.95 on PR W2000, p 0.0620363 (`dm.unconditional[a=hs, b=pot_gpd].p`). Sources: `reports/oos/w1000/backtest.json`, `reports/oos/w2000/backtest.json`, `reports/oos/tri_w1000/backtest.json`.

## Main finding on the price index (pass-dependent, borderline)

Holds on PR W1000 and PR W2000, not on TRI W1000. Quoted verbatim from [docs/results_review.md](docs/results_review.md):

> **H.** Only fhs and garch_evt are not rejected at 5% by any pre-declared coverage test (Kupiec, Christoffersen IND and CC, ES residual) at both primary levels in both windows.

On TRI W1000, garch_evt is rejected by the 0.99 ES residual test (p 0.0438). On PR W1000 the same test gives p = 0.0582, inside the borderline interval [0.01, 0.10] (D49 T3 and L1 in [docs/results_review.md](docs/results_review.md)). The full results, with each statement's passes and labels, are in [docs/report.md](docs/report.md).

## Quick start

Requirements:

- Windows with **Python 3.13** installed (`py -3.13 --version`). Python 3.14 is not supported (`requires-python = ">=3.13,<3.14"`).
- [uv](https://docs.astral.sh/uv/) 0.12 or later. `pyproject.toml` sets `python-preference = "only-system"`, because Windows Application Control blocks uv-managed interpreters on the development machine.

Setup (PowerShell, from the project root):

```powershell
uv sync --locked
```

`--locked` installs the exact versions in `uv.lock` and fails if the lockfile is out of date. The dashboard group is not installed here: it lives in its own environment (see [Dashboard](#dashboard)).

Checks:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
uv run --locked pytest --cov
py -3.13 -I docs\reference_values.py      # stdlib-only reference values (exit status 0 = all checks passed)
uv run --locked python -m niftytail check-config configs\base.toml
```

> **ENV-1 mitigation (decision D24, `docs/decisions.md`):** on the development machine, Windows Smart App Control blocks the newest compiled wheels of pandas, statsmodels and mypy. The project therefore pins older wheels that load. `tests/test_environment.py` fails loudly if the blocking returns. If Smart App Control blocks a console launcher such as `pytest.exe`, run it as a module: `uv run --locked python -m pytest`. Where Application Control also blocks coverage's C tracer (pytest prints a `no-ctracer` warning), `pytest --cov` still passes but can be slow (about half an hour on the development machine).

## Reproduce the study

One ordered path, from the download to the dashboard. Every command runs from the repository root, needs a clean tree for anything that writes, and logs no date or per-day value. The per-step details, flags and outputs are in [docs/reproduce.md](docs/reproduce.md) and in each step's decision. Durations are on the development machine (32 logical CPUs; [docs/reproducibility.md](docs/reproducibility.md)).

1. **Download** (owner, by hand; D23): the NIFTY 50 price-return (PR) history from niftyindices.com into `data/raw/`, one CSV per year, and the total-return (TRI) history into `data/raw_tri/` (file convention and licence quotes in [docs/data.md](docs/data.md)).
2. **Manifest**: `uv run --locked python -m niftytail validate configs\base.toml --init-manifest --retrieved YYYY-MM-DD --source-url URL` records names, sizes, sha256, row counts and date ranges in `data/raw/MANIFEST.toml` (once; it refuses to overwrite).
3. **Validation**: `validate configs\base.toml` (D25 hard errors; flags reported, never applied) and `validate-tri configs\base.toml` (D48).
4. **Threshold selection, on the training data only** (before any out-of-sample forecast was computed): `nmin-study` (about 40 s), `threshold-study` (the A3 simulation study, about 30 minutes with 31 workers), `threshold-select` (about 5 minutes), `threshold-select-residuals` (about 5 minutes) and `filter-select` (under a second). The selected threshold `q_selected = 0.88` is then committed in `configs/base.toml` (D37); `q_c = 0.88` and the F4 filter are fixed by D39.
5. **Out-of-sample runs**: `run configs\base.toml --window 1000` and `--window 2000` (D44), `tri-run configs\base.toml` (D48), each followed by its `--verify`; then `oos-publish`, `tri-publish`, `oos-blocks` + `oos-blocks-publish` (D45) and `xi-path` + `xi-path-publish` (D47). A `--verify` of the published runs took 89 s (PR W1000), 94 s (PR W2000) and 85 s (TRI W1000) with 31 workers.
6. **Figures**: `tl-blocks`, then `figures` (tracked SVGs from tracked JSON only; D51, D54) and, locally only, `figures-local` (D53; gitignored). Their `--verify` took 1 s, 5 s and 2 s.
7. **Dashboard**: see [Dashboard](#dashboard).

The run directories, the SVGs and the forecast key all include the generating commit (D44 (b)). A run at a later commit therefore creates new, equally valid run directories. Verified in the development repository with the owner's data (byte-identical reruns; docs/reproducibility.md). From this public copy: the tests and `demo-data --verify`. Commit IDs recorded in manifests and docs refer to the development repository.

## Using the model

The `forecast` command applies the backtested models (same config, same code path; D58) to the newest data and gives VaR and ES for the next trading day; the dashboard's Today section shows them with rupee amounts for a long position, the market from your own files, a crash calculator and a stress scenario.

1. Download the newest NIFTY 50 price-return file(s) from niftyindices.com into `data/live/` (gitignored; never into `data/raw/`). Keep the NSE file-name convention; the first live file must start the day after the last `data/raw/` file ends, with no gap or overlap. Set To to the last completed trading day, never a day whose close is not yet published.
2. Run `scripts\update.cmd` from the repository root (cmd or PowerShell; needs a clean tree). It runs validate-live (only if `data\live` exists), `fetch-api` (see [Automatic daily update](#automatic-daily-update)), `forecast` (writes `reports/live/<key>/forecast.json` and `series.json`, gitignored; an existing forecast is verified, not rewritten) and `forecast --check-run` on the published PR W1000 run (writes `check.json`). It prints `<step>: exit 0` per step, or the failing command's own error lines, and stops at the first failure.
3. Open the dashboard in local mode (no `NIFTYTAIL_PUBLIC`) and pick **Today**.

PowerShell or cmd:

```bat
scripts\update.cmd
```

The steps by hand (PowerShell):

```powershell
uv run --locked python -m niftytail validate-live configs/base.toml
uv run --locked python -m niftytail forecast configs/base.toml
uv run --locked python -m niftytail forecast configs/base.toml --verify
uv run --locked python -m niftytail forecast configs/base.toml --check-run reports/runs/e65780dc4f81b1cad5a3bdd88b0fd18bb69f9ba3585655814af338174c0b28c9
$env:UV_PROJECT_ENVIRONMENT = ".venv-dashboard"
uv run --locked --group dashboard python -m streamlit run app/dashboard.py
Remove-Item Env:UV_PROJECT_ENVIRONMENT
```

Without `data/live/`, `forecast` uses `data/raw/` alone. Today and "Day by day" must never be deployed or shared.


## Automatic daily update

The scheduled update asks EODHD, a licensed data vendor, for the newest NIFTY 50 end-of-day rows (`fetch-api`, D60); niftyindices.com and nseindia.com forbid automated collection. The free EODHD plan (20 calls a day, personal use) is enough: one call per run. Rows go to `data/api/` (gitignored) only after the overlap with the data you already have matches exactly (same session dates, same closes to 2 decimals). Nothing from EODHD is ever committed, published or shown in public mode.

1. Set the key once (new terminals only see it), in cmd or PowerShell:

   ```bat
   setx NIFTYTAIL_EODHD_KEY "<key>"
   ```

2. Run the update once by hand (after 16:30 India time):

   ```bat
   scripts\update.cmd
   ```

   It runs validate-live (only if `data\live` exists), fetch-api, forecast and the 20-day check-run (order per D61 (a)), printing `<step>: exit 0` per step, or the failing command's own error lines, and stops at the first failure.

3. Create the scheduled task once (weekdays at 20:30):

   ```bat
   schtasks /Create /TN "NIFTYTAIL update" /TR "\"<repo path>\scripts\update.cmd\"" /SC WEEKLY /D MON,TUE,WED,THU,FRI /ST 20:30
   ```

Conditions: the laptop must be on at that time; `forecast` refuses a dirty tree, so commit or stash first; a missed or failed run shows as the freshness warning in Today; `scripts\update.cmd` can be run by hand any time after 16:30; the key is never pasted into chats, issues or commits.


## Dashboard

A Streamlit dashboard (`app/dashboard.py`; decisions D55, D58, D59) in four sections: **Today** (local only), **Track record**, **How it works** and **Proof**. Every number is tracked JSON, the local output of `forecast`, the owner's own data, or closed-form arithmetic on those; the app imports no estimation code. Streamlit is never installed into the project `.venv` (D43): run it natively on Windows, from the repository root, in its own `.venv-dashboard` environment (D56), in PowerShell:

```powershell
$env:UV_PROJECT_ENVIRONMENT = ".venv-dashboard"
uv sync --locked --group dashboard
uv run --locked --group dashboard python -m streamlit run app/dashboard.py
# UI tests (streamlit.testing):
uv run --locked --group dashboard python -m pytest app/tests -o addopts=""
```

The browser opens by itself; the app is at http://localhost:8501 (Streamlit's URL lines are not printed, D59 pin (44)). The theme is dark (`.streamlit/config.toml`); Inter and IBM Plex Mono are served from `app/static/fonts/` with their OFL licences, so the app renders offline (no CDN).

Public-mode rule: any deployment (for example Streamlit Community Cloud, only after the D23 publication approval) **must set `NIFTYTAIL_PUBLIC=1`**. Without it, the Today section (market, next-day risk, crash calculator, stress) reads `reports/live/`, and "Day by day" (only when the D53 local figures exist with their recorded hashes) shows daily series derived from NSE data; neither may ever be deployed or shared.




## Deploy

Streamlit Community Cloud (only after the supervisor's approval, D23):

1. On [share.streamlit.io](https://share.streamlit.io), create an app from the public repository: branch `main`, main file `app/dashboard.py`.
2. Advanced settings: Python **3.13** (the project requires 3.13; the default is older), and in Secrets: `NIFTYTAIL_PUBLIC = "1"`.

Cloud installs from `app/requirements.txt` (the entrypoint directory is read before the repository root): streamlit and pyarrow pinned to the `uv.lock` versions and the `niftytail` package itself. `uv.lock` and `pyproject.toml` are unchanged. With the secret set, the app is in public mode: no `data/`, `reports/runs/` or `reports/live/` access, and the Today section is the synthetic demo.

## Data policy

No market data is stored in Git (decision D12). `data/` and `reports/runs/` are gitignored, and `tests/test_repo_hygiene.py` enforces this. Data acquisition is governed by decision **D23** (`docs/decisions.md`): the owner downloads manually for local use; no market data or derived daily series is ever committed or redistributed. Publishing the code is subject to D23's pre-publication checklist.
